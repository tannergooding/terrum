# CA1508: 163 analyzer-seconds in a small C# host library

> [!NOTE]
> AI-assisted draft based on measured SDK analyzer timings. No issue has been filed.

### Environment and impact

Windows x64 (10.0.26200), .NET SDK `11.0.100-rc.1.26425.128`,
MSBuild `18.11.0-1.26425.128+3551975be`; bundled
`Microsoft.CodeAnalysis.CSharp.NetAnalyzers.dll` file version
`11.1.26.42628`. The affected `net11.0` C# compiler-host library has 46
source files (about 836 KB), `AnalysisLevel=latest-all`,
`EnforceCodeStyleInBuild=true`, trimming/AOT analysis and warnings as
errors. CA1508 is otherwise disabled by default.

In a diagnostic Release rebuild the library reported **162.765
CA1508 analyzer-seconds** out of **187.173 aggregate core-project
analyzer-seconds**; trimming analysis reported 18.991, and CA5403/CA5390
just 0.485/0.443. That build took **2:10.41 wall time**. An earlier
snapshot had CA1508 at 181.500 analyzer-seconds even while CA5403/CA5390
dominated a 23-minute rebuild. Later forced Release rebuilds of the
three-project solution took **178.96 and 198.78 seconds wall time**,
with 178.503 and 198.195 seconds attributed by MSBuild to `Csc` tasks.
Already-cached restore took 0.46 seconds. Analyzer seconds can overlap
and must not be added or equated to elapsed time.

### Standalone scaling pattern (not a 163-second reproducer)

In a `net11.0` class library, set `AnalysisLevel=latest-all`,
`Nullable=enable` and `ReportAnalyzer=true`. A single method with
80 mutable `object?` locals and 256 distinct conditional branches
exercises CA1508's complete points-to/value-content analysis:

```csharp
public static class Conditions
{
    public static int Evaluate(int input)
    {
        var score = 0;
        object? v0 = input;
        object? v1 = input;
        // Declare v2 through v79 the same way (80 distinct locals total).

        if (input == 0)
        {
            v0 = new object();
            v1 = v0;
            // Assign v2 = v1; ...; v79 = v78;
        }
        else
        {
            v0 = v79;
            v1 = v0;
            // Assign v2 = v1; ...; v79 = v78;
        }
        if (v79 == v0) { score++; }

        // Repeat this whole branch/assignment/comparison block 255 more
        // times, using input == 1, ..., input == 255 (not a runtime loop).
        return score;
    }
}
```

Build with `dotnet build -c Release -t:Rebuild -p:ReportAnalyzer=true -v:diag`
and inspect the `CSharpAvoidDeadConditionalCode (CA1508)` analyzer timing.
Repeat with `-p:RunAnalyzers=false` for a total-analyzer-off control.

With the SDK above this case measured **0.755 CA1508
analyzer-seconds**, **2.98 seconds process wall time** with all analyzers
versus **1.26 seconds** with all analyzers off. It is a compact way to
exercise conditional-flow cost, **not** a minimized reproduction of the
library's 163-second hotspot. Which operation block is responsible remains
unknown; I would not attribute the extreme cost to this generated method.

### Isolation of the larger rebuild

A temporary high-priority `.globalconfig` suppressed **only CA1508,
CA5403 and CA5390** (`dotnet_diagnostic.<ID>.severity = none`);
other analyzers stayed enabled, including trimming and an independently
observed CA1050 diagnostic. Repeated no-restore Release `-t:Rebuild`
runs with identical quiet logging yielded:

| Mode | Wall seconds (three warmed runs) | `Csc` milliseconds |
|---|---|---|
| All analyzers disabled (`RunAnalyzers=false`) | 1.29 / 1.22 / 1.26 | 794 / 775 / 799 |
| Only these three rules disabled | 2.67 / 2.95 / 2.83 | 2205 / 2503 / 2355 |

The earlier default full-analysis rebuilds took 179-199 seconds on the
same machine. CA5403/CA5390 already cost <0.5 analyzer-seconds each in
this snapshot; the CA1508 attribution is the leading explanation for
the gap, but these comparisons do not isolate its exact wall-time
contribution. The temporary rule configuration was removed after the
experiment; useful analyzers remain enabled by default.

### Expected behavior and investigation

[CA1508](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca1508)
performs non-constant-value dataflow analysis; its documentation acknowledges
that it can increase compile time. The
[implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.CodeQuality.Analyzers/Maintainability/AvoidDeadConditionalCode.cs)
registers operation-block actions and, for eligible bodies, obtains a CFG
and calls `ValueContentAnalysis.TryGetOrComputeResult` with complete
points-to analysis. Can time be attributed per operation block around
that call (including CFG construction and result reuse) to isolate the
pathological body, then add a focused regression test? This is a
candidate investigation path, not a confirmed root cause. Unlike
CA5403/CA5390's byte-array issue, suppressing CA1508 permanently would
also discard useful maintainability diagnostics.
