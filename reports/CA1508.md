# CA1508 accounts for most of a three-minute full-analysis compiler rebuild

> [!NOTE]
> Agent-drafted upstream report; measurements and reproducer should be reviewed before posting.

**Upstream:** `dotnet/sdk` owns `Microsoft.CodeAnalysis.NetAnalyzers`
([repository migration notice](https://github.com/dotnet/roslyn-analyzers)).
This is distinct from the historical
[CA5403/CA5390](https://github.com/dotnet/roslyn-analyzers/issues/6737)
byte-array problem: those rules now take under 0.5 analyzer-seconds each
in the same project.

**Environment:** Windows x64; .NET SDK `11.0.100-rc.1.26425.128`,
MSBuild `18.11.0-1.26425.128+3551975be`, bundled
`Microsoft.CodeAnalysis.CSharp.NetAnalyzers.dll` file version
`11.1.26.42628`. The C# compiler-host library targets `net11.0`;
its 46 C# files total about 836 KB. `AnalysisLevel=latest-all`,
`EnforceCodeStyleInBuild=true`, `IsAotCompatible=true`, trimming
analysis and warnings as errors are enabled. CA1508 is otherwise
disabled by default.

**Standalone scaling case:** Run the accompanying `generate-ca1508.ps1`
with `-Conditions 256 -StateWidth 80 -OutputDirectory .\repro`,
then `dotnet build .\repro\AnalyzerRepro.csproj -c Release -t:Rebuild -v:diag`.
The generated project has independent build props, 80 mutable reference
locals and 256 sequential conditional branches in one method, with
different assignments on either side of each branch and subsequent
comparisons. The C# analyzer table lists
`Microsoft.CodeQuality.CSharp.Analyzers.Maintainability.CSharpAvoidDeadConditionalCode
(CA1508)`. With nullable analysis enabled, the standalone CA1508 time
was `0.755 s`, and the full run took `2.98 s` process wall time versus
`1.26 s` with `-p:RunAnalyzers=false`. It exercises CA1508 on conditional
alias flow but **does not** reproduce the 163-second magnitude;
the dominant operation block in the larger workload is not localized.

**Measured:** After CA5403/CA5390 were reduced by a byte-emission
change, a diagnostic Release rebuild took `2:10.41` wall time;
the core-project analyzer table reported `162.765 s` for CA1508
out of `187.173 s` total analyzer execution time. The trimming
analyzer reported `18.991 s`; CA5403 `0.485 s` and CA5390 `0.443 s`.
The earlier 23-minute build's CA1508 time was `181.500 s` despite
CA5403/CA5390 dominating its aggregate analyzer time; CA1508's
absolute cost remained high across those different source snapshots.
A later same-configuration Release forced rebuild took `198.78 s`
wall time and repeated at `178.96 s`; MSBuild's performance
summary assigned `198.195 s` and `178.503 s` respectively to the
three `Csc` tasks. The default, non-forced build immediately after
an analyzer-disabled rebuild took `3:20.97` for the build phase
and compiled all three projects; it did not skip deferred analysis.
An analyzer-disabled forced Release rebuild took `1.13 s`, but this
**disables all analyzers**, not just CA1508: that comparison only
bounds aggregate analyzer overhead. An already-cached restore took
`0.46 s`; fresh-machine restore and disk-cache effects were not measured.

**Selective-vs-total suppression:** A temporary high-priority
`.globalconfig` set only `dotnet_diagnostic.CA5403.severity = none`,
`dotnet_diagnostic.CA5390.severity = none`, and
`dotnet_diagnostic.CA1508.severity = none`. Other analyzers remained on
(an independent CA1050 diagnostic still appeared in the standalone
probe). The same no-restore Release `-t:Rebuild` command was alternated
six times after warm-up with quiet logging:

| Mode | Process wall time, three runs | MSBuild Csc task time, three runs |
|---|---|---|
| All analyzers off (`RunAnalyzers=false`) | 1.29 / 1.22 / 1.26 s | 794 / 775 / 799 ms |
| Only the three rules off | 2.67 / 2.95 / 2.83 s | 2205 / 2503 / 2355 ms |

The earlier default full-analysis forced rebuilds took `178.96–198.78 s`
on the same machine. A diagnostic three-rule-disabled rebuild reported
`27.552 s` **aggregate core analyzer execution time**, dominated by
`22.708 s` of trimming analysis, despite only `3.91 s` wall time:
concurrent analyzer execution means these numbers must not be added or
used as elapsed-time differences. The transient configuration was removed
after measurement; this report does not propose disabling useful rules
in the default build.

**Expected vs actual:** CA1508's dead-conditional diagnostics are useful,
but an opt-in maintainability rule should not account for most of a
multi-minute host-project compile of this size. The
[official rule reference](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1508)
explicitly warns that its non-constant-value data-flow analysis can
increase compile time on some codebases; this report provides concrete
scale and a project to profile.

**Implementation and open questions:** The
[SDK implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.CodeQuality.Analyzers/Maintainability/AvoidDeadConditionalCode.cs)
registers operation-block analysis, builds a control-flow graph for
eligible bodies and requests complete points-to and value-content
analysis. This is a plausible cost center, not proof of a specific
algorithmic defect or problematic method. The analyzer timing does
not identify which operation blocks dominate; a sampling trace or
per-method isolation would make this report more actionable. Do not
conflate it with CA5403/CA5390's separate byte-array scaling case.
