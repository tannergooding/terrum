# CA5403 spends over 20 minutes on byte-array opcode emission with no certificate use

> [!NOTE]
> Agent-drafted issue report; measurements and reproducer should be checked before posting.

**Upstream:** `dotnet/sdk`, which now owns `Microsoft.CodeAnalysis.NetAnalyzers`
([migration notice](https://github.com/dotnet/roslyn-analyzers)).
The [existing CA5403/CA5390 deprecation issue](https://github.com/dotnet/roslyn-analyzers/issues/6737)
already documents known performance problems; this report supplies a
standalone scaling case, not an assertion of two independent root causes.

**Environment:** Windows x64; SDK/MSBuild `11.0.100-rc.1.26425.128` /
`18.11.0-1.26425.128+3551975be`; bundled
`Microsoft.CodeAnalysis.NetAnalyzers.dll` file version `11.1.26.42628`
(product version `11.0.100-rc.1.26425.128+3551975be08744f0418857c5bed8ab1545c5dd47`).
The original project targeted `net11.0`, enabled `AnalysisLevel=latest-all`
and treated warnings as errors. CA5403 is normally disabled by default but
was enabled under this analysis policy.

**Standalone reproduction:** Run the accompanying `generate.ps1` with
`-Calls 2048 -OutputDirectory .\repro`, followed by
`dotnet build .\repro\AnalyzerRepro.csproj -c Release -t:Rebuild -v:diag`.
The generated project has independent build props and a single method that
repeats this eight-byte call at distinct sites:

```csharp
private void Bytes(params byte[] values) => _bytes.AddRange(values);
// In Emit():
Bytes(0x48, 0x89, 0xC8, 0x48, 0x89, 0xC8, 0x90, 0x90);
```

There are no certificate constructors or other cryptographic sinks.
Regenerate with `-Calls 0`, `128`, or `512` to inspect scaling; add `-Span`
to compare the same sites with `params ReadOnlySpan<byte>`. The diagnostic
log contains `Microsoft.NetCore.Analyzers.Security.DoNotHardCodeCertificate
(CA5403)` and the total analyzer time. Measure process wall time separately.

| Sites | Signature | Process wall time | CA5403 analyzer time | CA5390 analyzer time |
|---:|---|---:|---:|---:|
| 0 | `byte[]` | 1.51 s | <0.001 s | <0.001 s |
| 128 | `byte[]` | 0.89 s | 0.059 s | 0.004 s |
| 512 | `byte[]` | 1.35 s | 0.707 s | 0.024 s |
| 2,048 | `byte[]` | 53.97 s | 10.426 s | 42.179 s |
| 512 | `ReadOnlySpan<byte>` | 1.69 s | <0.001 s | <0.001 s |
| 2,048 | `ReadOnlySpan<byte>` | 1.71 s | <0.001 s | <0.001 s |

The first run includes project setup; the other process times are not a
statistical throughput comparison. At 2,048 sites, this reproduces a
severe slowdown without cryptographic sinks.

**Larger real-world scenario:** A C# compiler host with many native-opcode
byte-emission sites originally took
`23:00.29` wall time; the core-project analyzer table attributed `1324.598 s`
to CA5403, `693.321 s` to CA5390 and `2220.343 s` to all analyzers. The
post-change Release rebuild took `2:10.41` wall time with **all analyzers still
enabled**; core CA5403 took `0.485 s`, CA5390 `0.443 s`, all analyzers
`187.173 s`. These per-rule and aggregate figures are analyzer execution
times, which overlap when analyzers run concurrently; do not add them or
subtract them directly from wall time. Both measurements used
`ReportAnalyzer=true`; these were adjacent, not identical, revisions.

**Behavior-preserving workaround:** Changing the opcode helper from
`Bytes(params byte[] values)` to `Bytes(params ReadOnlySpan<byte> values)`
removed the isolated slowdown without disabling the rule. In the larger
project, additional small byte-producing calls were moved behind helpers;
before/after native PE output hashes matched for two measured samples.
The standalone same-input variant isolates the helper signature; the
larger-project measurements do not isolate every changed call site.

**Expected:** In the absence of any X.509 certificate construction, CA5403
should cost little and not dominate compilation simply because code
creates many short byte arrays. The published rule covers hard-coded data
passed to `X509Certificate`/`X509Certificate2`
([rule reference](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca5403)).

**Suspected mechanism, not a confirmed root cause:** CA5403 and CA5390 both
derive from the SDK's `SourceTriggeredTaintedDataAnalyzerBase`
([CA5403 implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.NetCore.Analyzers/Security/DoNotHardCodeCertificate.cs)).
Their simultaneous collapse after changing byte-array call sites suggests
common tainted-data flow work on array operations, even without
security-sensitive sinks. Analyzer attribution does not prove
that either rule exclusively consumes its reported time or identify the
internal operation; a profiler trace or fixed-revision A/B is still needed.
