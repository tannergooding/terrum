# CA5403: 10 seconds on byte-array opcode writes without certificate APIs

> [!NOTE]
> Drafted with AI assistance using measured SDK analyzer timings.

### Environment

Windows x64 (10.0.26200), .NET SDK `11.0.100-rc.1.26425.128`,
MSBuild `18.11.0-1.26425.128+3551975be`. The bundled
`Microsoft.CodeAnalysis.NetAnalyzers.dll` has file version
`11.1.26.42628`. Target framework `net11.0`; `AnalysisLevel=latest-all`
enables CA5403, which is disabled by default.

### Reproduction

Create a `net11.0` class-library project with `AnalysisLevel=latest-all`
and `ReportAnalyzer=true`. The entire relevant source pattern is:

```csharp
using System;
using System.Collections.Generic;

public sealed class Encoder
{
    private readonly List<byte> _bytes = new();
    private void Bytes(params byte[] values) => _bytes.AddRange(values);

    public int Emit()
    {
        Bytes(0x48, 0x89, 0xC8, 0x48, 0x89, 0xC8, 0x90, 0x90);
        // Repeat the line above at 2,048 distinct source locations in this method.
        // Do not use a runtime loop: the number of literal array creation sites matters.
        return _bytes.Count;
    }
}
```

There are **no certificate APIs or cryptographic sinks**. Build with
`dotnet build -c Release -t:Rebuild -p:ReportAnalyzer=true -v:diag`
and inspect the per-rule analyzer table; record process wall time separately.
Try 128, 512, then 2,048 distinct call sites. Finally change only the
helper signature to `Bytes(params ReadOnlySpan<byte> values)` and rebuild.
An unrelated CA1050 warning (type without namespace) does not prevent the
build.

| Call sites | Signature | Build process wall | CA5403 analyzer | CA5390 analyzer |
|---:|---|---:|---:|---:|
| 128 | `byte[]` | 0.89 s | 0.059 s | 0.004 s |
| 512 | `byte[]` | 1.35 s | 0.707 s | 0.024 s |
| 2,048 | `byte[]` | 53.97 s | 10.426 s | 42.179 s |
| 2,048 | `ReadOnlySpan<byte>` | 1.71 s | <0.001 s | <0.001 s |

The table comes from forced rebuilds on the same machine. A first build with
zero sites took 1.51 s including project setup, so sub-second wall-time
comparisons should not be interpreted as throughput benchmarks. The
2,048-site case is the independently reproducible result: switching **only
the helper parameter type** collapses both rule costs without changing the
eight-byte values written.

### Impact in the original workload

In a C# compiler host with many short opcode emissions, a Release rebuild
took **23:00.29 wall time**, while the core-project analyzer table reported
**1,324.598 analyzer-seconds for CA5403**, 693.321 for CA5390 and 2,220.343
for all analyzers. After replacing `params byte[]` with
`params ReadOnlySpan<byte>` and moving a few other byte-producing calls behind
helpers, the Release rebuild took **2:10.41 wall time**; CA5403 reported
0.485 analyzer-seconds and CA5390 0.443. Both rules remained enabled.
Two representative emitted PE images had identical SHA-256 hashes before
and after. These larger builds span other source changes; the standalone
case above isolates the parameter-type difference. Analyzer execution times
can overlap one another and elapsed build time -- they are not additive.

### Expected behavior and investigation

[CA5403](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca5403)
guards hard-coded data supplied to `X509Certificate`/`X509Certificate2`.
An assembly with no certificate APIs should not spend seconds on ordinary
byte-array opcode construction. The
[CA5403 implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.NetCore.Analyzers/Security/DoNotHardCodeCertificate.cs)
and [CA5390 implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.NetCore.Analyzers/Security/DoNotHardCodeEncryptionKey.cs)
both derive from `SourceTriggeredTaintedDataAnalyzerBase`. Is repeated
source/dataflow work performed before ruling out absent sinks, and can this
input become a performance regression test? That is a hypothesis, not a
confirmed root cause. An [older issue already tracks their known performance
problems and possible removal](https://github.com/dotnet/roslyn-analyzers/issues/6737);
this report contributes a reproducible no-sink input on the current SDK.
