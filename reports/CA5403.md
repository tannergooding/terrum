# CA5403 spends over 20 minutes on byte-array opcode emission with no certificate use

> [!NOTE]
> Agent-drafted issue report; measurements and reproducer should be checked before posting.

**Upstream:** `dotnet/sdk`, which now owns `Microsoft.CodeAnalysis.NetAnalyzers`
([migration notice](https://github.com/dotnet/roslyn-analyzers)).
The [existing CA5403/CA5390 deprecation issue](https://github.com/dotnet/roslyn-analyzers/issues/6737)
already documents known performance problems; this report supplies a specific
regression-sized workload rather than asserting a second, independent bug.

**Environment:** Windows x64; SDK/MSBuild `11.0.100-rc.1.26425.128` /
`18.11.0-1.26425.128+3551975be`; bundled
`Microsoft.CodeAnalysis.NetAnalyzers.dll` file version `11.1.26.42628`
(product version `11.0.100-rc.1.26425.128+3551975be08744f0418857c5bed8ab1545c5dd47`).
The project targets `net11.0`, enables `AnalysisLevel=latest-all`, and builds
with warnings as errors. CA5403 is normally disabled by default but is enabled
under this analysis policy.

**Reproduction:** The captured full-project before/after logs were taken from
development snapshots around `1633a6f`, not from two published, identical
revisions. To try the historical byte-array shape in the current source,
change `MachineCode.Bytes(params ReadOnlySpan<byte> values)` in
`NativeEmitter.cs` back to `params byte[]` in a scratch checkout; run
`dotnet restore Terrum.slnx`, then
`dotnet build Terrum.slnx --no-restore -c Release -t:Rebuild -p:ReportAnalyzer=true -v:diag`
with output redirected to a log. In the `Terrum.CodeAnalysis` analyzer timing
table, look for `Microsoft.NetCore.Analyzers.Security.DoNotHardCodeCertificate`.
For an isolated scaling workload, run `.\reports\repro\generate.ps1 -Calls 128`
and `dotnet build artifacts\profiles\analyzer-repro\AnalyzerRepro.csproj -c Release -t:Rebuild -v:diag`
from this repository; repeat with `-Calls 0`, `128`, `512`, and `2048`, recording the
CA5403 analyzer timing separately from total wall time. This generator creates
only a byte-emitting method with repeated eight-byte `params byte[]` calls;
there are no certificates or keys. It writes its temporary project under
ignored `artifacts\profiles\analyzer-repro`, with independent build props.
`-Span` switches the generated signature to `params ReadOnlySpan<byte>` for
a same-input comparison.

| Sites | Signature | Process wall time | CA5403 analyzer time | CA5390 analyzer time |
|---:|---|---:|---:|---:|
| 0 | `byte[]` | 1.51 s | <0.001 s | <0.001 s |
| 128 | `byte[]` | 0.89 s | 0.059 s | 0.004 s |
| 512 | `byte[]` | 1.35 s | 0.707 s | 0.024 s |
| 2,048 | `byte[]` | 53.97 s | 10.426 s | 42.179 s |
| 512 | `ReadOnlySpan<byte>` | 1.69 s | <0.001 s | <0.001 s |
| 2,048 | `ReadOnlySpan<byte>` | 1.71 s | <0.001 s | <0.001 s |

The first run includes project setup; the other process times are not a
statistical throughput comparison. At 2,048 sites, this **does** reproduce
a severe slowdown without a certificate or cryptographic key. The full
compiler's 20-minute analyzer cost additionally depends on its size and
source shape.

**Observed in the full Terrum project:** The pre-change Release rebuild took
`23:00.29` wall time; the core-project analyzer table attributed `1324.598 s`
to CA5403, `693.321 s` to CA5390 and `2220.343 s` to all analyzers. The
post-change Release rebuild took `2:10.41` wall time with **all analyzers still
enabled**; core CA5403 took `0.485 s`, CA5390 `0.443 s`, all analyzers
`187.173 s`. These per-rule and aggregate figures are analyzer execution
times, which overlap when analyzers run concurrently; do not add them or
subtract them directly from wall time. Logs were captured with
`ReportAnalyzer=true` and retained as local evidence; the two builds were on
adjacent, but not identical, revisions of a growing compiler.

**Behavior-preserving workaround:** In `NativeEmitter.cs`,
`MachineCode.Bytes(params byte[] values)` became
`MachineCode.Bytes(params ReadOnlySpan<byte> values)`; small byte-production
calls in `PeImage.cs` and the graph registrar were moved behind helpers.
The byte-oriented PE outputs before/after had matching SHA-256 hashes for
both measured samples. This does **not** disable CA5403. It changes the shape
of the code that the analyzer traverses without introducing certificate
operations. Reverting only the emitter signature in a fixed revision and
profiling again would better isolate which individual workaround causes the
improvement.

**Expected:** In the absence of any X.509 certificate construction, CA5403
should cost little and not dominate compilation simply because the project
creates many short byte arrays. The published rule covers hard-coded data
passed to `X509Certificate`/`X509Certificate2`
([rule reference](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca5403)).

**Suspected mechanism, not a confirmed root cause:** CA5403 and CA5390 both
derive from the SDK's `SourceTriggeredTaintedDataAnalyzerBase`
([CA5403 implementation](https://github.com/dotnet/sdk/blob/main/src/Microsoft.CodeAnalysis.NetAnalyzers/src/Microsoft.CodeAnalysis.NetAnalyzers/Microsoft.NetCore.Analyzers/Security/DoNotHardCodeCertificate.cs)).
Their simultaneous collapse after changing byte-array call sites suggests
common tainted-data flow work on array operations, even though this compiler
does not use the security-sensitive sinks. Analyzer attribution does not prove
that either rule exclusively consumes its reported time or identify the
internal operation; a profiler trace or fixed-revision A/B is still needed.
